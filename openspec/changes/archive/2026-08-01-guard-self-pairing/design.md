## Context

`pairing/` has no notion of "me". `TrustStore` (`trust.rs:52`) holds a path and a
fingerprint-keyed map and is never told which identity it belongs to, so it cannot
refuse its owner. `PairingService::new` (`service.rs:116-118`) loads the identity
immediately before the trust store, so the fingerprint is already in hand at the one
construction site that matters.

Self-pairing is reachable today because the broker mailbox pairs any two WebSocket
clients in a room (`broker/mailbox.go:54`) without caring that both come from one
process, and because every cryptographic step still agrees when both sides are the
same identity: SPAKE2 shares the password, and `shared_secret(own_pub)` is a
well-defined X25519 result, so the SAS matches too. Identity equality therefore has
to be an explicit check; it will never fall out of a handshake failure.

Constraints:

- The broker stays dumb. It never sees an unsealed identity and must not learn one,
  so the check cannot move server-side.
- The IPC surface is generated by tauri-specta from `specta_builder()`. Adding a
  command or event struct means regenerating `bindings.ts`. Avoidable here, so avoid
  it.
- UI copy rules from the project context apply to both new messages: no em dash, no
  "trusted"/"key"/"fingerprint"/"pair link".

## Goals / Non-Goals

**Goals:**

- A single enforced invariant: the trust store never holds the local fingerprint.
- Existing installs that already recorded a self-entry heal themselves.
- The user never sees a confirmation dialog for a pairing that cannot succeed.
- The two self-pair shapes (own code, shared identity) are told apart and worded
  differently.

**Non-Goals:**

- No new Tauri command and no new event struct, so `bindings.ts` is untouched.
- No guard added to `send_to`, offer verification, or the glare tiebreak. With the
  store invariant in place the local fingerprint can never be trusted, so those paths
  already refuse. Adding redundant checks there would spread the invariant instead of
  concentrating it.
- No change to how a *genuine* pairing works. This only closes a path that never had
  a legitimate outcome.
- Not a fix for two installs deliberately sharing an identity. They become unpairable
  and that is the intended answer, not a feature to design around.

## Decisions

### The store owns the invariant; the protocol sites own the message

`TrustStore` gains the local fingerprint and rejects a matching `add`. That is the
backstop, and it is what a unit test asserts.

The two `PairingService` sites (`service.rs:210` redeemer, `service.rs:395` shower)
still check independently. Not redundancy for its own sake: the shower's `add` sits
*after* the confirm dialog, so relying on the store alone would make the user approve
a pairing and then watch it fail. The protocol checks exist to fail early and to
produce a good message; the store check exists so the invariant holds no matter who
calls.

*Alternative considered:* store check only. Smallest diff, worst UX, and it leaves
`0x00`-vs-`0x02` indistinguishable. Rejected.

*Alternative considered:* protocol checks only. Leaves `TrustStore::add` able to
write a self-entry for any future caller, which is exactly the gap that produced this
bug. Rejected.

### `0x02` as a third reply byte

The reply frame is currently `0x01 ‖ sealed(identity)` for confirm and a lone `0x00`
for decline (`service.rs:402-412`, `service.rs:203-217`). Adding `0x02` for "same
device" is one match arm on each side and no envelope change.

Reusing `0x00` would surface "The other device didn't add this one." for a case where
nobody declined anything — actively misleading, and in the same-install case the
"other device" is the one the user is holding.

Old builds receiving `0x02` fall into the existing `_ =>` arm and report the generic
unexpected-reply error. Acceptable: both ends of a pairing are the user's own
installs, and the failure is still a refusal.

### A live-code registry on `PairingService`

To say "that's this device's own code" rather than the generic shared-identity
message, the redeemer needs to know the codes it is itself showing. `show_pair_code`
currently spawns a detached task and keeps nothing.

Add `active_codes: Arc<Mutex<HashSet<String>>>` holding normalized phrases. Insert in
`show_pair_code`, remove in the spawned task's cleanup so both the completion path
and the `PAIR_TIMEOUT` path clear it.

**`redeem_pair_code` must read it before the exchange, not after.** Implementation
found this the hard way: the showing side detects the self-pair, replies `0x02`, and
its session ends, which runs the cleanup — all before the redeemer has read the
reply off the mailbox. Consulting the set at the point of failure therefore always
answered "not one of ours" and produced the shared-identity message for a plain
own-code self-pair. The read happens once, up front, and the chosen message is
carried down to whichever refusal fires. The question it answers is the right one
anyway: at the moment the user hit connect, was this a code we were showing?

This is deliberately *not* the guard. A pre-flight bail on a matching code would miss
the shared-identity case and the reflected-identity case, and it would put
correctness in a cache that can go stale if cleanup is ever missed. A wrong message
is a cosmetic bug; a missed guard is not.

### Who reports the refusal

The device that scanned or typed the code reports it, as an ordinary `Err` from
`redeem_pair_code`. The shower logs, sends `0x02`, and closes without emitting a
user-facing event.

Rationale: in the same-install case both sides are one app, and emitting on both
would show the user two errors for one action. The redeemer is also the side the user
just acted on, so its error lands where attention already is.

The cost lands on the cross-machine shared-identity case: that user's code appears to
die silently, the same way an expired code does. Recorded as an open question rather
than papered over.

### `in_memory()` keeps its signature

`TrustStore::in_memory()` has six call sites in `offer.rs` tests plus three in
`trust.rs`, none of which care about self-rejection. Give it an empty-string owner
fingerprint (a real fingerprint is 64 hex chars, so it can never collide) and add
`in_memory_owned_by(fp)` for the tests that do exercise the guard. Keeps churn off
unrelated tests without weakening the production path.

`TrustStore::load` takes the fingerprint as a second argument. One production caller.

### Purge on load, not on read

`load` drops a self-entry and writes the cleaned store back immediately, rather than
filtering in `list()`/`get()`. Filtering on read would leave the bad row on disk
forever and require every accessor to remember the rule. A one-time write at startup
is cheaper and leaves the file honest.

## Risks / Trade-offs

- **Stale `active_codes` entry picks the wrong message** → Cleanup runs on both the
  normal and timeout paths of the spawned task. Worst case is the wrong one of two
  refusal messages; the refusal itself comes from the fingerprint comparison, not the
  registry.
- **Cross-machine shared-identity user sees nothing on the showing device** →
  Accepted for now, matching existing silent code expiry. See Open Questions.
- **A user who genuinely restored a backup onto a second machine cannot pair the
  two** → Intended. The shared-identity message names the situation. `/fp` routing is
  ambiguous with two registrants on one fingerprint anyway, so allowing the pairing
  would produce a worse, harder-to-diagnose failure downstream.
- **`0x02` against an older peer build** → Falls into the existing unexpected-reply
  arm. Still a refusal, just a vaguer one.
- **Purge writes on every startup if the drop check is written carelessly** → Only
  persist when an entry was actually removed.

## Migration Plan

No user action and no data migration. The first start after this ships purges any
self-entry from `trust.json`; genuine peers are untouched. Rolling back to the
previous build leaves the cleaned file readable, since the schema is unchanged.

## Open Questions

- **Should the showing device emit `PairingEvent::Error` too? Deferred, shipped
  without it.** The redeemer owns the message, as decided above. The cross-machine
  shared-identity case therefore leaves the showing device silent, the same as an
  expired code. Deferred rather than settled because the cost is real but small, and
  because nobody has hit it yet: the same-install case is the one users actually
  reach, and it is fully covered. If it does come up, the shower already has
  everything it needs at the bail point (`ShowTask::run`) to emit one, and
  `an_install_cannot_redeem_its_own_code` asserts the no-confirm behaviour that must
  not regress alongside it.
- Should the Devices page show this install's own fingerprint or self-identity, so a
  user hitting the shared-identity message can confirm the diagnosis? Out of scope
  here, but it is the natural follow-up.
- `PAIR_TIMEOUT` is a 120s const, so the timeout branch of the `active_codes` cleanup
  is covered structurally (it shares one removal line with the completion branch) but
  not by an assertion. Making the timeout injectable would close that, and would pay
  for itself in any future test that needs an expired code.
